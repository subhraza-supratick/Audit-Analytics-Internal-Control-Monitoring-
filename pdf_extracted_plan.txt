 System
 Deloitte-oriented flagship Data Analyst portfolio project — complete concept, features, architecture,

1. Project Objective
Build an end-to-end audit analytics application that ingests synthetic financial data, validates and transforms it, stores it in
PostgreSQL, applies SQL-based audit tests and statistical/ML anomaly detection, assigns explainable risk scores, and
presents exceptions through dashboards and an investigation workflow.
Core question: Which transactions deserve attention, why were they flagged, how risky are they, and what financial
exposure might they represent?

6. Audit Rules / Features
  Duplicate invoice detection — same/similar vendor, date, amount and reference characteristics.
  Duplicate payment detection — repeated payment for the same invoice/vendor/amount.
  Weekend transaction detection — flags transactions occurring on Saturday/Sunday for review.
  After-hours transaction detection — flags transactions outside defined operating hours.
  Round-amount detection — identifies large, perfectly rounded transaction amounts for review.
  Approval-threshold violation — compares transaction amount with the required approval level.
  Split-purchase detection — identifies several related purchases that collectively exceed an approval threshold.
  Unusual vendor activity — compares current vendor behavior with historical patterns.
  Employee expense anomaly — identifies expenses unusually large relative to an employee's history.
  Duplicate employee expense — detects repeated employee/date/amount/description patterns.
  Employee-vendor relationship check — flags potential relationships requiring investigation, without treating them as proof
 of misconduct.
7. Risk Scoring
Use a transparent, explainable score rather than relying entirely on ML. Combine rule severity, transaction value, frequency,
historical deviation, and control impact. Normalize the result to 0–100.
  0–30: Low
  31–60: Medium
  61–80: High
  81–100: Critical
 The exact weights must be documented in the repository and should be based on the rules you actually implement. An
exception is a review signal, not proof of fraud.
8. Machine Learning Layer
Isolation Forest is appropriate as an additional unsupervised anomaly-detection layer when labeled fraud outcomes are
unavailable. Possible features include transaction amount, transaction frequency, vendor transaction count, employee

Recommended flow: rule-based score + statistical signals + ML anomaly score → final explainable risk score. Keep the

9. SQL Analytics
Build approximately 20–30 meaningful queries and document them in GitHub. Cover joins, GROUP BY/HAVING,
subqueries, CTEs, window functions, date analysis, duplicate detection, ranking, aggregation, and exception rates.
Example duplicate-invoice query:
 SELECT vendor_id, invoice_date, amount, COUNT(*) AS invoice_count FROM invoices GROUP BY
vendor_id, invoice_date, amount HAVING COUNT(*) > 1;
Example vendor-payment analysis:
 SELECT vendor_id, SUM(amount) AS total_payment, COUNT(*) AS payment_count FROM payments GROUP
BY vendor_id ORDER BY total_payment DESC;

12. RBAC
  Admin: users, rules, thresholds, datasets and all analytics.
  Auditor: investigate exceptions, assign issues, add notes, update status and generate reports.
  Analyst: upload datasets, run analytics and view dashboards.
  Viewer/Management: read-only executive dashboards and reports.
 
13. Exception Investigation Workflow
Each detected issue becomes a structured Audit Exception with an ID, transaction, vendor, amount, violated rule, risk score,
explanation, status, assigned auditor, review notes and resolution.
Recommended states: OPEN → UNDER REVIEW → RESOLVED or OPEN → FALSE POSITIVE.
Maintain an audit log for important actions, recording who changed what and when.
